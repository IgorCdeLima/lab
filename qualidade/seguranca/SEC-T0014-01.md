# SEC-T0014-01 - Hash do pip no requirements-lock.txt nao e conferido porque o pip ja vem na imagem base

## Descricao

O `requirements-lock.txt` traz `pip==26.2.1` com dois hashes, e o estagio `lock` instala com `pip install --no-cache-dir --require-hashes -r requirements-lock.txt`. Porem a imagem `python:3.13.15-slim` ja traz o `pip 26.2.1`. O pip ve o requisito como satisfeito, **nao baixa o artefato e nao confere o hash**:

```
Requirement already satisfied: pip==26.2.1 in /usr/local/lib/python3.13/site-packages (from -r requirements-lock.txt (line 37)) (26.2.1)
Successfully installed build-1.6.1 click-8.5.0 packaging-26.3 pip-tools-7.6.1 pyproject-hooks-1.3.3 setuptools-84.0.0 wheel-0.48.0
```

Com os dois hashes do `pip` adulterados numa copia, o `docker compose build lock` **passa** (exit 0). Os outros 7 pacotes sao conferidos (hash de `click` removido -> "Hashes are required"; o Dev tambem testou com `pyproject-hooks`).

O criterio da T-0014 ("inclui pip") e o `pip freeze --all` (8 pacotes, mesmas versoes) passam, mas nenhum dos dois prova que o pip veio do artefato com aquele hash. O mesmo vale para `requirements-dev.txt` (`pip==26.2.1`, linha 498) no estagio `dev`, anterior a esta tarefa (T-0009).

## Impacto

O pip que roda o `pip-compile` e gera os hashes de toda a aplicacao e confiado pela **tag** da imagem base, nao pelo hash do travado. Um pip adulterado na imagem (tag reapontada, cache/registry comprometido) nao seria barrado pelo `--require-hashes`, que da a impressao de cobrir o pip. Severidade baixa: a imagem oficial e a mesma fonte de confianca do proprio interpretador; o risco depende da decisao, ja levada ao humano, de fixar a base por digest.

## Como explorar / reproduzir

Copia descartavel no scratchpad (`git archive HEAD | tar -x -C <scratch>/copia1`):

```bash
C=<scratch>/copia1
sed -i 's/71138adf1f4ca900/71138adf1f4ca901/; s/f6ad667e89a1fe78/f6ad667e89a1fe79/' $C/requirements-lock.txt
docker compose --project-directory $C -p t0014-segc --profile lock build --no-cache lock   # exit 0 (falha esperada)
docker run --rm --entrypoint pip python:3.13.15-slim --version                              # pip 26.2.1 ja na base
```

Com `--force-reinstall` no `RUN` do estagio (so na copia): hash adulterado -> `THESE PACKAGES DO NOT MATCH THE HASHES` (exit 1); travado original -> exit 0, `Successfully installed ... pip-26.2.1 ...` (8 pacotes).

## Recomendacao de correcao

- Estagio `lock`: `pip install --no-cache-dir --require-hashes --force-reinstall -r requirements-lock.txt` (testado na copia, acima). Avaliar o mesmo no estagio `dev` para o `pip` do `requirements-dev.txt`.
- Alternativa/complemento: fixar a imagem base por digest (decisao ja em "Passos do humano" da T-0014).
- Teste de aceite: adulterar so o hash do `pip` numa copia -> `build lock` falha.
