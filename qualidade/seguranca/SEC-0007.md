# SEC-0007 - Estagio lock instala o pip-tools sem hash e com 6 dependencias indiretas sem versao

<!-- NUNCA registrar senhas, tokens, chaves ou dados pessoais reais. -->

## Descricao

A T-0009 travou com versao e hash todas as dependencias das imagens `runtime` e `dev` (SEC-0003). O estagio `lock`, que **gera** esses hashes, ficou fora do controle:

```
FROM python:3.13.15-slim AS lock
RUN pip install --no-cache-dir pip==26.2.1 pip-tools==7.6.1
```

- `pip` e `pip-tools` tem versao fixa, mas **sem hash**.
- As dependencias indiretas do pip-tools nao tem versao em lugar nenhum. Na imagem construida em 30504a2 vieram: `build==1.6.1`, `click==8.5.0`, `packaging==26.3`, `pyproject_hooks==1.3.3`, `setuptools==84.0.0`, `wheel==0.48.0`. Cada `build` do estagio resolve de novo no PyPI.
- A imagem base e referenciada so pela tag (`python:3.13.15-slim`, sem `@sha256:`). Isso ja vale para `base` e `runtime` (anterior a esta tarefa), mas aqui afeta tambem a ferramenta de travamento.

## Impacto

Quem controlar uma versao nova de `click`, `build` ou outra indireta do pip-tools roda codigo no container `lock`. Esse codigo pode gravar nos `requirements*.txt` hashes de um artefato adulterado, e a revisao humana dificilmente percebe um hash trocado num diff de 1.100 linhas. A partir dai o `--require-hashes` passa a proteger o artefato errado. Ver tambem o SEC-0008: o mesmo container tem escrita no repositorio inteiro.

Severidade baixa: so roda quando alguem regenera o travado, sem ataque demonstrado. Hoje o resultado e limpo: regenerei os travados numa copia e sairam **identicos** aos commitados, e o osv-scanner nao achou vulnerabilidade nos 8 pacotes do estagio.

## Como explorar / reproduzir

```bash
APP_PORT=8309 docker compose -p t0009-seg --profile lock build lock
docker run --rm --entrypoint pip t0009-seg-lock freeze --all
# build, click, packaging, pyproject_hooks, setuptools, wheel: nenhum fixado no Dockerfile
grep -n "pip-tools" Dockerfile   # sem --require-hashes, sem --hash
```

Nao houve ataque real; o achado e de configuracao.

## Recomendacao de correcao

- Criar `requirements-lock.in` (`pip-tools==7.6.1`) e um `requirements-lock.txt` gerado com `pip-compile --generate-hashes --allow-unsafe` (que inclui o `pip`), e instalar no estagio com `pip install --no-cache-dir --require-hashes -r requirements-lock.txt`. O primeiro travado sai do proprio servico `lock`; depois ele se mantem como os outros.
- Opcional (vale para todos os estagios): fixar a imagem base por digest (`python:3.13.15-slim@sha256:...`), atualizando o digest junto com a tag.
- Teste: remover um hash do `requirements-lock.txt` -> `docker compose build lock` falha.
