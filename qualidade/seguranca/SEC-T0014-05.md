# SEC-T0014-05 - O lock reaproveita os hashes do travado existente e preserva um hash adulterado

## Descricao

A correcao do BUG-T0014-01 (commit `371fbbe`) copia os `.txt` atuais para `/tmp` antes do `pip-compile` (`cp /in/*.in /out/*.txt /tmp/`). Isso preserva os pinos, como se queria. Mas o `pip-compile` 7.6.1 tem `--reuse-hashes` **ligado por padrao** (`pip-compile --help`: "Improve the speed of --generate-hashes by reusing the hashes from an existing output file"). Resultado: para cada pacote cujo pino nao muda, o `lock` **copia os hashes do arquivo antigo** em vez de recalcula-los a partir do indice.

Consequencias observadas:

1. **Hash adulterado sobrevive a regeneracao.** Na copia, troquei o 1o hash de `starlette==1.7.0` no `requirements.txt` por `sha256:000...0` e rodei o `lock`: exit 0, o hash falso continua no arquivo. A frase "regenera os tres travados identicos" deixou de ser uma conferencia independente: o `lock` so devolve o que recebeu.
2. **Os hashes de sdist ficaram por reaproveitamento, nao porque "todos os pacotes tem wheel".** Com `--no-reuse-hashes` (mesmos `.in`, mesmos pinos) o `requirements.txt` cai de 744 para 720 linhas `sha256`: 24 hashes de sdist somem, as versoes ficam **iguais** e o hash falso e substituido pelo verdadeiro. A Entrega (correcao 2) diz "nenhum hash de sdist foi removido, pois todos os pacotes tem wheel"; o motivo real e o reaproveitamento. Com `--only-binary :all:` nos travados esses hashes de sdist sao inertes (o pip recusa sdist na instalacao), mas o arquivo commitado nao e o que uma compilacao limpa gera.

Nao ha bypass da instalacao: o `pip install --require-hashes` continua recusando qualquer artefato cujo hash nao esteja listado (hash falso -> install falha, so negacao de servico).

## Impacto

O processo oficial de regeneracao nao detecta nem corrige um hash inserido ou trocado nos `requirements*.txt` (por um commit malicioso, um merge mal resolvido ou edicao a mao, que o README proibe mas nada impede). Um hash **a mais** de um artefato malicioso seria preservado em toda regeneracao futura; para ser explorado, o atacante ainda precisaria servir esse artefato na mesma versao (indice espelhado ou comprometido), por isso a severidade e **baixa**. A defesa que resta e a revisao humana do diff dos `.txt`, que hoje e grande (centenas de linhas de hash) e dificil de revisar.

## Como explorar / reproduzir

Copia descartavel no scratchpad (`git archive HEAD | tar -x -C <scratch>/copia`), projeto Compose proprio:

```bash
cd <scratch>/copia
# 1) adulterar o 1o hash de starlette==1.7.0 em requirements.txt (script Python de 5 linhas:
#    localizar 'starlette==', trocar os 64 hex do 1o '--hash=sha256:' por zeros)
docker compose -p t0014-seg-lock run --rm lock          # exit 0
grep -A2 '^starlette==' requirements.txt                # hash 000...0 continua

# 2) mesmo arquivo adulterado, com --no-reuse-hashes
docker compose -p t0014-seg-lock run --rm lock sh -ec "cp /in/*.in /out/*.txt /tmp/ && \
  pip-compile --generate-hashes --allow-unsafe --strip-extras --quiet --no-reuse-hashes \
  --pip-args '--only-binary=:all:' requirements.in && cat requirements.txt > /out/requirements.txt"
diff <(grep -E '^[a-z0-9_.-]+==' requirements.txt.orig) <(grep -E '^[a-z0-9_.-]+==' requirements.txt)  # vazio: versoes iguais
grep -c sha256 requirements.txt.orig requirements.txt   # 744 -> 720; hash falso some
```

Controle: com os 3 travados originais o `lock` (como esta) gera os 3 arquivos byte a byte identicos (`cmp`), dono = usuario do host.

## Recomendacao de correcao

- Acrescentar `--no-reuse-hashes` aos 3 `pip-compile` do servico `lock`. Os pinos continuam preservados (vem do `.txt` copiado); so os hashes passam a ser recalculados do indice a cada execucao. Custo: execucao mais lenta.
- Aceitar a mudanca intencional de uma vez: os 3 travados perdem os hashes de sdist (inertes com `--only-binary :all:`). Registrar na Entrega e corrigir a frase "nenhum hash de sdist foi removido".
- Teste de aceite: adulterar um hash numa copia, rodar o `lock` -> o hash verdadeiro volta; travados originais -> segunda execucao identica a primeira.
- Opcional (processo): no PR, conferir que o diff dos `.txt` so muda pacotes que os `.in` explicam.
