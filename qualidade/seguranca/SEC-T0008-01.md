# SEC-T0008-01 - Container app sem no-new-privileges e com o conjunto padrao de capabilities

## Descricao

A T-0008 resolveu o principal (SEC-0004): o uvicorn roda como `uid=10001(app)` e as capabilities efetivas do processo sao zero. Faltam, porem, as duas camadas seguintes da OWASP para o servico `app`:

- `NoNewPrivs: 0`: o processo pode ganhar privilegio executando binario setuid. A imagem tem 9 (`su`, `mount`, `umount`, `passwd`, `chsh`, `chfn`, `newgrp`, `gpasswd`, alem de `su` repetido em outro caminho).
- `CapBnd: 00000000a80425fb`: o conjunto limite e o padrao do Docker (CHOWN, DAC_OVERRIDE, SETUID, SETGID, NET_RAW etc.). E isso que um binario setuid recebe ao rodar.

## Impacto

Sem falha demonstrada hoje. O risco e de defesa em profundidade. Se um atacante conseguir executar codigo como `app` (por uma falha futura no upload ou numa dependencia), um bug num binario setuid da camada do sistema o levaria de volta a root dentro do container. A varredura da T-0008 lista CVEs sem correcao em `util-linux` (pacote de `mount`/`su`), `pam` e `shadow`; ver SEC-T0008-02. Com `no-new-privileges` e `cap_drop: [ALL]`, esse caminho fecha, mesmo que o binario continue vulneravel.

Severidade baixa: laboratorio sem exposicao publica e sem execucao de codigo conhecida.

## Como explorar / reproduzir

```bash
APP_PORT=8308 docker compose -p t0008-seg up -d --build
docker exec t0008-seg-app-1 sh -c 'grep -E "^(Uid|CapEff|CapBnd|NoNewPrivs)" /proc/1/status; find / -xdev -perm -4000 -type f 2>/dev/null'
# -> Uid 10001, CapEff 0, CapBnd 00000000a80425fb, NoNewPrivs 0; 9 binarios setuid
```

O endurecimento foi testado e **nao quebra a aplicacao**. Mesma imagem, mesma rede e mesmo volume do projeto `t0008-seg`:

```bash
docker run -d --name t0008-seg-hard --network t0008-seg_default -e POSTGRES_HOST=db ... \
  -v t0008-seg_uploads:/uploads -p 8318:8000 --cap-drop ALL --security-opt no-new-privileges t0008-seg-app:latest
# -> CapBnd 0, NoNewPrivs 1; GET /health 200; POST /produtos com PNG 303
```

## Recomendacao de correcao

- No servico `app` do `docker-compose.yml`:
  ```yaml
  security_opt:
    - no-new-privileges:true
  cap_drop:
    - ALL
  ```
  A porta interna e 8000 (acima de 1024), entao `NET_BIND_SERVICE` nao faz falta.
- Opcional, avaliar numa tarefa propria: `read_only: true` com `tmpfs: /tmp` (OWASP regra 8). Isso **nao** foi testado aqui.
- Opcional: remover o bit setuid na imagem runtime (`find / -xdev -perm -4000 -exec chmod u-s {} +`). Com `no-new-privileges`, ele perde o efeito de qualquer forma.
- Teste: `/proc/1/status` com `NoNewPrivs: 1` e `CapBnd: 0000000000000000`; health 200 e upload 303.
