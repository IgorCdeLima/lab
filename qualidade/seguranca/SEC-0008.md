# SEC-0008 - Servico lock roda como root com o repositorio inteiro montado para escrita, inclusive .githooks

<!-- NUNCA registrar senhas, tokens, chaves ou dados pessoais reais. -->

## Descricao

O servico `lock` do `docker-compose.yml` monta a pasta do projeto inteira, para escrita, e roda como root (uid 0):

```yaml
lock:
  volumes:
    - .:/work
```

Ele so precisa ler `requirements.in` e `requirements-dev.in` e escrever `requirements.txt` e `requirements-dev.txt`. Com a montagem atual o container tambem alcanca:

- `.githooks/`: o repositorio usa `core.hooksPath=.githooks`, ou seja, `pre-commit` e `commit-msg` rodam **no host** a cada commit;
- `app/`, `Dockerfile`, `docker-compose.yml` e os `.in`;
- `.env`, se existir na copia do humano (fora do Git, com as credenciais).

O `pip-compile` baixa pacotes do PyPI. Se um candidato so tiver sdist, o pip executa o codigo de build dele (setup.py/backend) para ler os metadados. Hoje isso nao acontece: conferi que todos os pacotes dos dois travados tem wheel para a plataforma (`pip download --only-binary=:all:` passou).

## Impacto

Codigo malicioso que rode no `lock` (sdist de uma dependencia nova, ou uma indireta adulterada do pip-tools, ver SEC-0007) consegue gravar em `.githooks/pre-commit` e assim executar comandos no host, fora do container, no proximo `git commit` de qualquer agente ou do humano. Tambem pode ler o `.env` e alterar codigo da aplicacao junto com os travados. Arquivos criados ficam com dono root no host (o `chown` so cobre os dois `.txt`).

Severidade baixa: exige um pacote comprometido no momento de rodar o `lock`, que e acao rara e manual; sem ataque real demonstrado.

## Como explorar / reproduzir

Numa copia descartavel (`git archive HEAD | tar -x -C <scratchpad>/seg-copia`):

```bash
docker compose -p t0009-segc --profile lock run --rm lock sh -c \
  'id -u; touch /work/.githooks/PROVA_ESCRITA && echo escreveu_em_githooks'
# saida: 0 / escreveu_em_githooks
ls -l .githooks/PROVA_ESCRITA   # -rw-r--r-- root root (arquivo vazio, inofensivo)
git config --get core.hooksPath # .githooks (no worktree da tarefa)
```

## Recomendacao de correcao

- Montar so o necessario. Exemplos: mover os `.in`/`.txt` para nao precisar da raiz, ou montar arquivos especificos (`./requirements.in:/work/requirements.in:ro`, `./requirements-dev.in:/work/requirements-dev.in:ro`) e uma pasta de saida para escrita, copiando os `.txt` dela; nunca `.githooks`, `.env` nem `app/`.
- Rodar sem root: `user: "${UID:-1000}:${GID:-1000}"` no servico (dispensa o `chown`), ou `USER` sem privilegio no estagio `lock`.
- Impedir execucao de build de sdist na resolucao: `pip-compile --pip-args "--only-binary=:all:"` (falha cedo se surgir pacote so com sdist; a decisao de aceitar um sdist vira explicita).
- Teste: `docker compose run --rm lock sh -c 'touch /work/.githooks/x'` deve falhar; `id -u` diferente de 0; `lock` continua gerando os mesmos arquivos.
