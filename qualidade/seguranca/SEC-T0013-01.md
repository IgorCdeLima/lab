# SEC-T0013-01 - Erro de banco capturado como SQLAlchemyError vira 503 sem nenhum registro no log

## Descricao

O P2 da T-0013 ampliou o `except` de `OperationalError` para `SQLAlchemyError` em dois pontos de `app/main.py`:

- `_pagina` (listagem, `GET /` e a pagina de erro do `POST`);
- o `commit` de `POST /produtos`.

Nos dois, o erro vira a pagina 503 "Banco de dados indisponivel no momento..." e **nada e registrado** alem da linha de acesso do uvicorn (`"GET / HTTP/1.1" 503`). Unica excecao: o commit ambiguo do P3, que faz `log.warning` (so com o nome do arquivo, sem o erro).

Antes da T-0013 o mesmo silencio valia so para `OperationalError` (banco fora ou lento, que o operador ve tambem pelo `/health`). Agora entram tambem `ProgrammingError` (tabela ou coluna inexistente, SQL quebrado), `IntegrityError` (restricao violada), `DataError` e afins: defeito de codigo, esquema divergente ou dado inesperado ficam **indistinguiveis** de "banco fora" e sem rastro. O `/health` responde 200 nesses casos (`SELECT 1` funciona), entao nem o monitoramento percebe.

A pagina para o usuario esta correta (sem traceback, SQL ou nome de tabela; CWE-200 continua atendido). O problema e so do lado do operador.

## Impacto

- Nao ha forma direta de um atacante explorar: nenhuma entrada do formulario provoca esses erros (testei a bateria de entradas extremas, so 422/303).
- Um defeito ou uma alteracao indevida no esquema (ex.: tabela renomeada, restricao adicionada) deixa o cadastro inteiro em 503 "banco indisponivel" sem log que explique a causa: diagnostico lento e sem trilha para analise posterior (MITRE CWE-778: "Hide Activities", sem trilha forense).
- Severidade **baixa**: afeta deteccao e diagnostico, nao confidencialidade nem integridade.

## Como explorar / reproduzir

Alvo isolado: projeto Compose `t0013-seg`, porta 8313, commit `8b34628`. `psql` dentro do container `db` com as variaveis do proprio container (nenhuma senha digitada).

```bash
U=http://127.0.0.1:8313
psql(){ docker compose -p t0013-seg exec -T db sh -c "psql -qtA -U \"\$POSTGRES_USER\" -d \"\$POSTGRES_DB\" -c \"$1\""; }

# IntegrityError no commit do POST
psql "ALTER TABLE produto ADD CONSTRAINT seg_t0013 CHECK (nome <> 'proibido')"
curl -s -o /dev/null -w '%{http_code}\n' -F nome=proibido -F valor=1,00 -F fornecedor=f $U/produtos   # 503
psql "ALTER TABLE produto DROP CONSTRAINT seg_t0013"

# ProgrammingError na listagem e no POST
psql "ALTER TABLE produto RENAME TO produto_seg"
curl -s -o /dev/null -w '%{http_code}\n' $U/                                                        # 503
curl -s -o /dev/null -w '%{http_code}\n' $U/health                                                  # 200
psql "ALTER TABLE produto_seg RENAME TO produto"

docker compose -p t0013-seg logs app --since 5m | grep -vE '" (200|303) '
```

Resultado: as respostas sao 503 com o aviso generico (correto) e o log so tem as linhas de acesso `... 503 Service Unavailable`; nenhum `ERROR`/`WARNING`, nenhum nome de excecao ou `sqlstate`.

## Recomendacao de correcao

- Nos dois `except SQLAlchemyError`, registrar no log do servidor (`log.warning` ou `log.error`) **a classe da excecao e o `sqlstate`** (`getattr(erro.orig, "sqlstate", None)`), e a rota. Ex.: `log.error("erro de banco em %s: %s sqlstate=%s", rota, type(erro).__name__, sqlstate)`.
- **Nao** registrar `str(erro)` inteiro: a mensagem do SQLAlchemy traz `[parameters: ...]` com os dados digitados (nome, fornecedor). Se quiser o traceback (`log.exception`), criar o engine com `hide_parameters=True` (OWASP Logging Cheat Sheet: nao registrar dados alem do necessario; nunca string de conexao nem senha).
- Opcional: distinguir no log `OperationalError` (indisponibilidade) dos demais (provavel defeito), com nivel `error` para estes.
- Teste automatico: com monkeypatch de `IntegrityError` (o teste do P2 ja existe), conferir com `caplog` que sai um registro com a classe e sem os valores do formulario.
