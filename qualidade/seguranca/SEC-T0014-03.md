# SEC-T0014-03 - Servico lock roda sem root mas sem no-new-privileges e com as capabilities padrao

## Descricao

O servico `lock` agora roda como `1000:1000`, com `read_only` e so os 3 `.in` (leitura) e os 3 `.txt` (escrita) montados. Isso foi conferido e fecha o SEC-0008 na parte de usuario e montagem. Falta o resto da regra de privilegio minimo ja padronizada no Brain:

```
CapEff:     0000000000000000
CapBnd:     00000000a80425fb      (conjunto padrao do Docker)
NoNewPrivs: 0
setuid: /usr/bin/umount /usr/bin/mount /usr/bin/chsh /usr/bin/chfn /usr/bin/newgrp /usr/bin/su /usr/bin/gpasswd /usr/bin/passwd
```

## Impacto

O `lock` e justamente o container que executa codigo de terceiros (pip-tools e, se surgir um sdist, o backend de build dele; ver SEC-T0014-04). Com uma falha num dos 8 binarios setuid, esse codigo voltaria a root dentro do container. O alcance continua limitado (sem raiz do projeto, sem `.githooks/`, sem `.env`), por isso severidade baixa, defesa em profundidade.

## Como explorar / reproduzir

```bash
docker compose -p t0014-seg --profile lock run --rm --no-deps lock sh -c \
  'id; grep -E "^(CapEff|CapBnd|NoNewPrivs)" /proc/self/status; find / -perm -4000 -type f 2>/dev/null'
```

Experimento com a correcao (copia descartavel, `docker run` com a imagem `lock` e as mesmas montagens do servico, `--security-opt no-new-privileges:true --cap-drop ALL`): `CapBnd 0000000000000000`, `NoNewPrivs 1`, `pip-compile` do `requirements-lock.in` e do `requirements.in` funcionou e os travados sairam **identicos** aos commitados.

## Recomendacao de correcao

No servico `lock`:

```yaml
security_opt: ["no-new-privileges:true"]
cap_drop: [ALL]
```

Teste: `docker compose run --rm lock grep -E "^(CapBnd|NoNewPrivs)" /proc/self/status` mostra `0000000000000000` e `1`; `lock` continua gerando os mesmos arquivos.
