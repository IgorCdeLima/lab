### Script do teste negativo (copia descartavel)

```sh
S=<scratchpad>; mkdir -p $S/neg && git -C <worktree> archive HEAD | tar x -C $S/neg
h=$(grep -A2 '^starlette==' $S/neg/requirements.txt | grep -o 'sha256:[0-9a-f]*' | head -1 | cut -d: -f2)
Z=$(printf '0%.0s' $(seq 64)); sed -i "s/$h/$Z/" $S/neg/requirements.txt
docker compose --project-directory $S/neg -f $S/neg/docker-compose.yml -p t0014-rev-neg run --build --rm lock
grep -c $Z $S/neg/requirements.txt           # 0
for f in requirements.txt requirements-dev.txt requirements-lock.txt; do cmp $S/neg/$f <worktree>/$f; done   # sem saida
```

## Observacao (nao bloqueante, nao e defeito do codigo)

- A primeira tentativa rodou dois `lock` em paralelo (copias `lock` e `neg`). Os dois falharam apos cerca de 15 min com `ReadTimeoutError` em `files.pythonhosted.org`, durante o calculo dos hashes. Com `--no-reuse-hashes`, o `pip-compile` baixa todos os arquivos.
- Nada foi gravado: o `cat > /out/...` so roda no fim, e os `.txt` das copias ficaram intactos.
- Repetido sozinho, o `lock` levou 2m59s, com rc=0.
- Causa confirmada pelo humano (2026-10-02): o computador ficou alguns minutos sem rede enquanto ele mudava de local. Nao foi o paralelo nem o `lock`.
- O que fica do episodio: sem rede, o `lock` falha de forma segura, sem gravar nada nos `.txt`.

## O que NAO foi verificado

- Execucao isolada na copia limpa (`lock`): falhou por rede (acima) e nao foi repetida. A copia `neg` cobre o mesmo caso, pois os 3 arquivos sairam identicos aos commitados.
- Docker Desktop no Windows (montagem de arquivo isolado e posse dos `.txt`): sem ambiente Windows.
- Host com uid real diferente de 1000 usando `LOCK_UID`/`LOCK_GID`.
- `.txt` ausente no host (o bind mount vira pasta de root): fora do fluxo normal.
- `--only-binary` com um pacote que so tem sdist: nao ha esse caso nas dependencias atuais.
- O `pip` da imagem `runtime` continua vindo da imagem base sem hash. Depende da decisao do digest em "Passos do humano".
