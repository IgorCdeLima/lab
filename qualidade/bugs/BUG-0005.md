# BUG-0005 — Valor com 27 ou mais dígitos na parte inteira gera erro 500 (`decimal.InvalidOperation` no `quantize`)

## Como reproduzir

Stack do Revisor (`APP_PORT=8102 docker compose -p t0002-rev up -d --build`), commit `baabd17`:

```
curl -X POST http://localhost:8102/produtos --data "nome=X&valor=111111111111111111111111111&fornecedor=F"
# (27 dígitos) → 500 Internal Server Error
```

Log: `decimal.InvalidOperation: [<class 'decimal.InvalidOperation'>]`.

Direto no parser:

| Entrada | `interpretar_valor` |
|---|---|
| `'1' * 26` | `11111111111111111111111111.00` (depois vira 422 pelo teto; ok) |
| `'1' * 27` | `InvalidOperation` → 500 |

## Esperado

Cartão da T-0002: validações com a mensagem de erro **na própria página**. A correção do BUG-0003 também exigia que nenhuma entrada lançasse exceção. Um valor enorme deve dar 422 com "O valor máximo é R$ 99.999.999,99".

## Obtido

Erro 500. O usuário perde o que digitou nos outros campos. Diferente do BUG-0004, esse valor pode ser digitado ou colado num navegador comum.

## Causa raiz

`Decimal(normal).quantize(Decimal("0.01"))` usa o contexto padrão do `decimal`, com precisão de 28 dígitos. Quando o resultado com duas casas passa de 28 dígitos (27 ou mais na parte inteira), o `quantize` sinaliza `InvalidOperation`. Os padrões `\d+` não limitam a quantidade de dígitos.

O defeito **já existia no `da476c0`** (mesma linha do `quantize`) e **não foi detectado no VER-0003**. Foi uma lacuna da revisão anterior, que não testou valores com muitos dígitos (a Entrega já listava "valores extremos" como não verificados).

## Correção sugerida (a decidir pelo Dev)

Limitar a quantidade de dígitos antes de converter (por exemplo, no máximo 8 na parte inteira, coerente com `NUMERIC(10,2)`), ou comparar com o teto antes do `quantize`, ou tratar `InvalidOperation` como valor inválido. Acrescentar ao `test_valor_invalido` um caso com 27 ou mais dígitos, por exemplo `"1" * 30`.
