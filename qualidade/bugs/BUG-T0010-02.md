# BUG-T0010-02 - PNG de 16 bits em cinza com transparencia (tRNS) perde a transparencia

## Como reproduzir

1. Gerar com o Pillow 12.3.0 um PNG cinza de 16 bits com cor transparente:

   ```python
   im = Image.new("I;16", (8, 8), 30000)
   im.putpixel((0, 0), 1000)
   im.save(buf, "PNG", transparency=1000)   # reabre como I;16, info {'transparency': 1000}
   ```

2. Enviar em `POST /produtos` com campos validos (ou chamar `imagens.processar_imagem(buf.getvalue())`).
3. Reabrir o arquivo gravado e ler o alfa do pixel `(0, 0)`.

## Esperado

303 e o pixel `(0, 0)` (valor 1000, a cor declarada transparente) gravado com alfa 0; os demais com alfa 255. A regra do `requisitos.md` diz que a transparencia do PNG e mantida ("PNG real 8x8 com transparencia -> gravado como PNG com canal alfa"), e o cartao lista a conversao coerente de modo com transparencia como armadilha.

## Obtido

303, arquivo `PNG RGBA` com **todos os pixels opacos**: `(0, 0)` = `(4, 4, 4, 255)`. A transparencia some sem aviso.

## Evidencia

Commit `0a00687` (codigo de `d3e4004`), projeto `t0010-rev`, porta 8110, e chamando `app.imagens` no container:

```
entrada: I;16 {'transparency': 1000}
apos reescala: L {'transparency': 1000}
saida: RGBA {} alfa(0,0)= (4, 4, 4, 255)
```

Na aplicacao rodando: `PNG I;16 + tRNS=1000` -> 303, gravado `PNG RGBA (8, 8)`, alfa `(0,0)` = 255.

## Causa raiz

`_modo_para` (correcao do BUG-T0010-01, commit `3c35d3e`) reescala `I;16` para `L` com `convert("I").point(v/257 + 0.5).convert("L")`, mas o `info["transparency"]` continua com o valor de 16 bits (1000). Em seguida `convert("RGBA")` procura o valor 1000 numa imagem de 8 bits, nao acha nenhum pixel, e tudo fica opaco. Nao e regressao: no codigo anterior (`convert("RGBA")` direto do `I;16`) a imagem ja saia toda branca e opaca.

Correcao possivel (decisao do Dev): reescalar tambem o valor de `transparency` (`round(t / 257)`), ou montar o alfa a partir da mascara `im == t` antes de reescalar (mais exato: dois niveis de 16 bits diferentes podem cair no mesmo nivel de 8 bits). Teste: PNG `I;16` com `tRNS` -> pixel da cor transparente com alfa 0 e os outros com 255.

Fora deste bug (comportamento do proprio Pillow, so registro): PNG RGB de 16 bits e reduzido pelo decodificador do Pillow pegando o byte alto (1000 -> 3, nao 4); diferenca de 1 nivel, aceitavel.
