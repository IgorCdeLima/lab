# BUG-T0010-03 - Banco lento ou indisponivel vira erro 500 em qualquer pagina, inclusive no 503 de "Servidor ocupado"

**Pre-existente (nao introduzido pela T-0010).** Achado durante o teste manual do CS-08; registrado para nao ficar omitido. Nao bloqueia a T-0010.

## Como reproduzir

Forma deterministica (projeto Compose proprio):

1. `APP_PORT=8110 docker compose -p t0010-rev up -d --build`
2. `docker compose -p t0010-rev stop db`
3. `curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:8110/` -> `500`
4. `curl -s -o /dev/null -w '%{http_code}' -F nome= -F valor=x -F fornecedor= http://127.0.0.1:8110/produtos` -> `500` (deveria ser 422 de validacao)
5. `docker compose -p t0010-rev start db`

Forma em que apareceu (CS-08): app com teto de 2000 MB (override fora do repositorio), 6 rodadas de 10 `curl` paralelos com WebP RGBA 7071 x 7071 num host de 3,4 GB com swap em 3434/3738 MB. Na rodada 4: 2 x 303, **2 x 500**, 6 x 503.

## Esperado

Nenhuma resposta 500. Com o banco lento ou fora, uma pagina de indisponibilidade (ex.: 503 "Servidor ocupado, tente de novo." ou equivalente), sem traceback.

## Obtido

500 Internal Server Error. No log do `app`:

```
File "/code/app/main.py", line 149, in cadastrar
    return _pagina(
File "/code/app/main.py", line 109, in _pagina
    produtos = sessao.scalars(
...
psycopg.errors.ConnectionTimeout: connection timeout expired
```

## Evidencia

- Commit `a64c4d1` (codigo de `4ede09f`), projeto `t0010-rev`, porta 8110.
- `docker logs t0010-rev-app-1`: 2 linhas `POST /produtos HTTP/1.1" 500`, 4 ocorrencias de `ConnectionTimeout`; nenhuma excecao do Pillow.
- `free -m` logo depois: swap 3434 de 3738 MB usados (o Postgres foi paginado; `connect_timeout` de 3 s estourou ao abrir conexoes novas do pool).
- Na `main`: `_pagina` (linha 108) faz a mesma consulta sem tratamento e `app/db.py` tem o mesmo `connect_timeout: 3` -> comportamento anterior a tarefa.

## Causa raiz

`_pagina` sempre lista os produtos do banco, inclusive para responder erro de validacao (422) e "Servidor ocupado" (503). Nenhuma rota trata `sqlalchemy.exc.OperationalError` / `psycopg.errors.ConnectionTimeout`, entao banco lento ou fora vira 500. A T-0010 so torna o caso mais provavel: a decodificacao de 50 MP ocupa ~1,3 GiB e, num host pequeno, empurra o Postgres para o swap.

Correcao possivel (decisao do Dev / Engenheiro, fora da T-0010): tratar erro de conexao com o banco com uma pagina 503 sem a lista (handler global), ou renderizar 422/503 sem consultar o banco quando ele falhar. Teste: banco indisponivel -> 503, sem `Traceback`. Candidata a entrar na T-0015 (limites e `restart` do `app`) ou numa tarefa propria.
